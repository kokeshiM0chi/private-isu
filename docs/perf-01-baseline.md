# 基準スコア

計測日: 2026-11-02

Macのcolimaで、改善前のGo実装を計測した。別環境のスコアとは比べられない。同じ環境での改善前後の比較に使う。計測時点で、`webapp/golang` と `benchmarker` は `master`（`730e8a4`）と差分がない。

## 環境

| 項目 | 値 |
| --- | --- |
| Colima | 4 CPU、メモリ5GiB |
| app | 2 CPU、メモリ1GiB |
| mysql | 2 CPU、メモリ2GiB |
| ベンチ | 同じVMのコンテナから実行 |
| InnoDBバッファプール | 128MB（既定値のまま） |
| データ量 | posts約1.2GB（画像BLOB込み） |

appとmysqlの制限は `webapp/compose.kokeshi.yml` で変えている。

## 結果

各3回。生の出力は `results/`、一覧は `results/summary.tsv` にある。

| 遅延 | 判定 | スコア | 成功 | 失敗 |
| --- | --- | --- | --- | --- |
| なし | `pass:true` | 4,355 / 4,478 / 4,478 | 4,204 / 4,317 / 4,329 | 0 / 0 / 0 |
| 100ms | `pass:false` | 0 / 0 / 0 | 4 / 4 / 4 | 6 / 6 / 6 |

改善の比較は、この表の中央値を基準にする。

## 100msが失敗する理由

リソース不足ではなく、DBとの往復回数が原因である。100msでは `POST /login` と `POST /register` が10秒でタイムアウトし、初期チェックで打ち切られる。

`GET /` を1回実行して確かめた。

| 項目 | 遅延なし | 100ms |
| --- | --- | --- |
| 応答時間 | 0.84秒 | 30.48秒 |

1回の `GET /` でプリペアドステートメントの準備と実行が各132回発生した。準備と実行で合わせて264往復になり、100ms × 264 ≒ 26秒が待ち時間の大半を占める。

この基準は、0点から抜け出すことが最初の目標になる。往復回数を減らす改善が直接効く。

## 環境の調整で分かったこと

最初はmysqlが `webapp/compose.yml` の既定の1 CPUのままだった。

| 条件 | スコア | 失敗 |
| --- | --- | --- |
| mysql 1 CPU、遅延なし | 0 / 0 / 0 | 58 / 57 / 64 |
| mysql 2 CPU、遅延なし | 4,355 / 4,478 / 4,478 | 0 / 0 / 0 |

1 CPUのときは、ベンチ中にmysqlがCPU上限に張り付き、VM全体は66〜75%が空いていた。メモリは約50%で、ディスク待ちもほぼなかった。

## 参考: 以前のインデックスが残っていた状態

`comments(post_id, created_at)` のインデックスが残り、mysqlが1 CPUの状態では、遅延なしで13,874、2,075、10,586だった。このときのばらつきの原因は調べていない。

このインデックスは基準の計測前に削除した。作り直す場合は次を実行する。

```sql
CREATE INDEX idx_comments_post_created ON comments (post_id, created_at);
```

## 注意

`/initialize` は追加行を消すだけで、インデックスや画像の移行は元に戻らない。計測は `scripts/practice.sh measure` で行い、毎回DBを基準データへ戻す。
